# Data Promotion SOAR App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Splunk SOAR app (SOAR SDK) whose actions drive the `promotion_control` REST API, including promoting from an edge host by hostname or GUID.

**Architecture:** Plain, SDK-free modules hold the logic (`client.py` HTTP + error mapping, `times.py`, `forwarders.py`) and are unit-tested with `httpx.MockTransport`. `app.py` declares the asset, params/outputs and thin `@app.action` wrappers that build a client from the asset and call those modules.

**Tech Stack:** Python 3.13/3.15, splunk-soar-sdk 8.0.2, httpx, pytest, uv, `soarapps` CLI (installed with `uv tool install splunk-soar-sdk`).

**Spec:** `docs/superpowers/specs/2026-11-26-soar-app-design.md`

## Global Constraints

- App lives in `soar_app/`; scaffolded with `soarapps init`; `requires-python = ">=3.13, <3.16, !=3.14.*"` as generated.
- App version `1.0.0`; product name `Data Promotion`; product vendor `Splunk Inc.`; license `Apache-2.0`; app type `siem`.
- API base: asset `base_url` + `/services/data_promotion`; auth header `Authorization: Bearer <token>`.
- Final job statuses: `completed`, `incomplete`, `failed`, `cancelled`.
- `forwarders` on promote/estimate is required; `*` alone means all; never send an empty value to the API.
- Every handled failure raises `soar_sdk.exceptions.ActionFailure(message)`.
- Package output: `dist/data_promotion_soar-1.0.0.tgz` (`dist/` is gitignored).
- Commit only after the user OKs committing (repo rule); steps say "commit" as the checkpoint.

## Review Focus

1. A hostname given with different case or with a domain suffix (`HF-OSL-0001` vs `hf-osl-0001`) — case-insensitive exact match; FQDN vs short name is NOT matched (fail with the value named). Test in Task 2.
2. Duplicate values that resolve to the same GUID (`hf-osl-0001, 5A8D…`) — sent once. Test in Task 2.
3. `*` mixed with names (`*, hf-osl-0001`) — rejected as ambiguous intent. Test in Task 2.
4. Non-JSON error bodies (proxy HTML, 500 from splunkd) — failure message carries status and a truncated body, not a JSON traceback. Test in Task 1.
5. `job_id` with whitespace or slash from a playbook datapath — stripped; `/` rejected before building the URL. Test in Task 3.

### Task 2: Times and forwarder resolution

**Files:**
- Create: `soar_app/src/times.py`, `soar_app/src/forwarders.py`
- Test: `soar_app/tests/test_times.py`, `soar_app/tests/test_forwarders.py`

**Interfaces:**
- Consumes: `PromotionClient.get` (Task 1).
- Produces:
  - `def normalize_time(value: str | int | float | None, default: str | None = None) -> str | None` — ISO 8601 → epoch seconds as a string; epoch and Splunk modifiers pass through stripped; empty → `default`.
  - `@dataclass class Resolved: value: str; guid: str; hostname: str`
  - `def resolve_forwarders(spec: str, rows: list[dict]) -> tuple[list[str], list[Resolved]]` — returns `(["*"], [])` for `*`, else `(guids_deduped_in_order, resolutions)`. Raises `ActionFailure`.
  - `def resolve_with_client(client: PromotionClient, spec: str, sourcetype: str | None = None) -> tuple[list[str], list[Resolved]]` — fetches `GET forwarders` (no sourcetype filter, so a host that lacks the sourcetype is still resolved and the API reports the real problem) and calls `resolve_forwarders`.

    - `test_separators`: `"hf-osl-0001, hf-ber-0001"` and `"hf-osl-0001 hf-ber-0001"` → two GUIDs in order.
    - `test_star` → `(["*"], [])`.

    - `test_unknown_named`: `"hf-nope"` → ActionFailure containing `hf-nope`.
    - `test_ambiguous_named`: `"dup"` → ActionFailure containing `dup` and both GUIDs.

### Task 3: Read actions

**Files:**
- Modify: `soar_app/src/app.py`
- Create: `soar_app/src/jobs.py` (helpers below)
- Test: `soar_app/tests/test_jobs.py`, `soar_app/tests/test_actions_read.py`

**Interfaces:**
- Consumes: `client_for`, `PromotionClient`, `resolve_with_client`.
- Produces in `jobs.py`: `FINAL_STATUSES = frozenset({"completed","incomplete","failed","cancelled"})`; `def clean_job_id(value: str) -> str` (strip; empty or containing `/` → ActionFailure); `def enrich_job(job: dict) -> dict` (adds `is_final: bool`, `search: "promote_job=<job_id>"`).
- Actions (identifier = function name; outputs are `ActionOutput` subclasses; list actions return `list[...]`, one result row per item):

| Function | action_type, read_only | Params | Output |
|---|---|---|---|
| `list_forwarders` | investigate, True | `sourcetype: str \| None` | `ForwarderOutput`: guid, hostname, label, status, last_seen, version, max_bytes_per_job, sourcetypes: list[str], days, files, bytes, earliest, latest |
| `list_data` | investigate, True | `sourcetype: str \| None`, `forwarder: str \| None` (GUID/hostname, resolved to exactly one GUID) | `CatalogOutput`: sourcetype, day, files, bytes, earliest, latest, forwarders, agents, agent, updated_at (all-forwarder rows come from a search and carry `agents`; per-forwarder rows come from the KV store and carry `agent`) |
| `list_jobs` | investigate, True | `status: str \| None`, `limit: int = 50` | `JobOutput` |
| `get_job` | investigate, True | `job_id: str` (cef_types `["data promotion job id"]`, primary) | `JobOutput` |
| `get_job_tasks` | investigate, True | `job_id` | `TaskOutput`: job_id, agent, agent_host, status, files_total, files_done, bytes_read, events_staged, events_skipped, events_bad, started_at, finished_at, message |
| `verify_job` | investigate, True | `job_id` | `VerifyRowOutput`: index, sourcetype, host, count:int |

`JobOutput` fields: job_id (cef `["data promotion job id"]`), status, is_final, search, message, sourcetype, earliest, latest, forwarders, forwarders_count, agents_expected, agents_reported, agents_failed, files_total, files_done, bytes_read, events_staged, events_indexed, index_filter, target_index, submitted_by, submitted_at. Numeric fields `int | None`. Search-backed endpoints return numbers as strings and KV rows as floats: coerce through a `to_int(value) -> int | None` helper in `jobs.py` (`"120344"`→120344, `1.0`→1, `""`/None→None) before building outputs; test it in Step 1.

Summaries via `soar.set_summary(...)` with a small `ActionOutput` per action: list actions `{"total": n}`; `get_job` `{"status", "is_final"}`; `verify_job` `{"events"}`. `soar.set_message(...)` one line, e.g. `"Job 2026… is running (3/10 forwarders reported)"`.
